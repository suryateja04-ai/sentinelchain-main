Federated Hospital Units

Extending "AI-Agent Based Early Prediction and Clinical Guidance Support for Sepsis" with privacy-preserving federated learning

B. Sainath (23241A05T1) · C. Surya Teja (23241A05T7) · M. Shiva Ganesh (23241A05W5) · P. Sahith (23241A05W9)
Guide: Dr. Krishna Chythanya N, Professor

1Purpose

In Phase-I all training data was pooled in one place. Real hospitals cannot do that: patient records are protected and usually cannot leave the hospital. This report describes how the system is turned into a federated system in which every hospital has its own unit. Each unit keeps its patient data inside the hospital, trains on it, and runs predictions according to its own data. Hospitals improve a shared model by exchanging only model updates through a central server, which checks every update before using it.

In one sentence The data stays in each hospital; only signed and validated model updates travel to the central server, which combines them into a global model and sends it back to every hospital for the next round.

2Reference process

The federated unit follows the standard agentic federated learning process shown in the reference poster (Agentic Federated Learning for Privacy-Preserving Disease Prediction). Only the process is taken from it; the dataset, models and clinical pipeline remain those of this project.

4One federated round

Universal updateThe server sends the current global model to every hospital unit. Every hospital starts round 1 from the same initial weights.
Local trainingEach unit trains on its own training windows for one local epoch (Adam, learning rate 0.001, batch 256, positive-class weight from the federation's counts). With FedProx a proximal term keeps the local model close to the global one.
SigningThe unit signs its update and sample count with HMAC-SHA256 using the secret key it received at registration.
Security LayerThe server recomputes the signature. An update from an unknown client, or one changed in transit, is dropped.
Orchestrator AgentValidates every verified update (Section 6) and filters out faulty or malicious ones. Each decision is logged with its reason.
Federated AggregationAccepted updates are averaged, weighted by each hospital's number of training windows. If every update is rejected, the global model is kept unchanged.
Global model and evaluationThe new global model gets a SHA-256 digest. Each hospital reports its validation AUROC, F1 and accuracy, and the server keeps the best round by window-weighted validation AUROC.

After the last round, every hospital personalises the global models on its own validation patients (Section 8) and deploys them inside its unit.

Federated preprocessing

Phase-I fitted the median imputer and standard scaler on pooled training data. In the federated unit they are fitted without moving rows, in two rounds:

  1. Each hospital sends the minimum and maximum of every variable; the server merges them into a global range.
  2. Each hospital sends, per variable, a 4,096-bin histogram over that range, the number of observed values, and their sum and sum of squares. Each hour is counted once for every training window it appears in, as in Phase-I.

The server reads the global median from the merged histogram (accurate to one bin width). Because missing values are replaced by that median, the global mean and standard deviation can then be computed exactly from the sums.

Models in the federation

ModelHow it is federated
GRU, LSTM, Temporal CNN, Logistic RegressionFederated averaging of weights over rounds (FedAvg or FedProx)
LightGBM, XGBoostTrees cannot be averaged weight by weight. Each hospital trains its own and shares the trained model; the federation's score for a tree type is the window-weighted average of the hospitals' models
Random Forest, Linear SVMLeft out: both had ensemble weight 0 in Phase-I, and Random Forest took about 122 ms per window with a 682 MB file

6Security Layer and Orchestrator Agent

Security Layer

At registration each hospital receives a 32-byte secret key. Before sending, the hospital computes HMAC-SHA256(key, weights + sample count). The server recomputes it and accepts the update only if the two match, using a constant-time comparison. This detects updates changed in transit and updates from unregistered senders.

Orchestrator Agent rules

No.CheckRejects
1Every value in the update is finiteUpdates containing NaN or infinity (a crashed or faulty client)
20 < sample count ≤ the hospital's registered training windowsA client inflating its count to gain more weight
3Size of the change from the global model ≤ 3 × the median size of the other hospitals' changesScaled (boosted) updates that would dominate the average
4Cosine similarity between the change and the other hospitals' mean change ≥ −0.1Sign-flipped updates that push the model the wrong way

Rejected updates are left out of that round only, so a hospital that recovers can take part again in the next round.

Attack simulation

To show that the checks work, any client can be made faulty during an experiment: scale (change × 20), signflip, noise, nan, or tamper (changed after signing). The round log then records which stage rejected it and why.

7FedAvg and FedProx

FedAvg: w(t+1) = Σ_k ( n_k / Σ_j n_j ) · w_k(t+1) over accepted hospitals k FedProx: local objective at hospital k L_k(w) + (μ / 2) · || w − w(t) ||² μ = 0.01 by default then the same weighted average on the server

FedAvg averages the hospitals' models in proportion to their training windows. When hospitals are very different (non-IID), their local models can drift apart and the average gets worse. FedProx adds a proximal term that keeps each local model close to the current global model, which usually makes training more stable on non-IID data. Both are run and compared.

8Each hospital runs on its own data

After federated training, every hospital personalises the shared models on its own validation patients, exactly as Phase-I did on the pooled validation set:

  • Isotonic calibration per model, so probabilities match that hospital's own sepsis rate.
  • Ensemble weights found with SLSQP on that hospital's validation log-loss.
  • Alert threshold by the same rule: best F1 with recall ≥ 0.50, on that hospital's validation patients.

So Hospital A and Hospital B share what they learn but each gets an ensemble and threshold that fit its own patients. The unit's artifacts (preprocessor, models, calibrators, weights, threshold, model card) are stored in the hospital's own folder, and that hospital's Sepsis Prediction Agent loads them.

The audit record written by the orchestrator includes the hospital ID, the federated model version and the list of hospitals the model was trained on, next to the SHA-256 of the input window.

9Three-agent pipeline in each hospital unit

Phase-I used ten agents. Several of them were single steps rather than decisions (loading a file, writing a log line), so the pipeline is reduced to three agents, each owning one complete responsibility. Every hospital unit runs the same three agents with its own personalised models.

AGENT 1
Data Gathering and Preprocessing
  • Gathers the latest 16-hour window (16 × 39) from the hospital's record
  • Fingerprints the input as received (SHA-256)
  • Validates shape and history length; sets impossible values to missing
  • Reports vitals and labs observed
  • Applies the federated imputer and scaler
  • Measures slope and 4-hour change of key vitals
AGENT 2
Sepsis Prediction
  • Scores the window with the GRU, LSTM, Temporal CNN, Logistic Regression, LightGBM and XGBoost models
  • Calibrates each score with the hospital's isotonic calibrators
  • Combines them with the hospital's ensemble weights
  • Decides the alert with the hospital's own threshold
  • Reports the hospital's precision, sensitivity, specificity and alerts per 100 windows at that threshold
AGENT 3
Explainability and Clinical Guidance
  • Occlusion: contribution of every observed signal, in percentage points
  • Flags latest values outside adult reference ranges
  • Writes fixed decision-support guidance
  • Blocks diagnosis, treatment and medication wording
  • Builds the clinician report

The orchestrator is not an agent. It runs the three agents in order, records each one's status, time and output, stops the run if Agent 1 finds the data unusable, and writes the audit record: trace ID, hospital ID, SHA-256 of the input window, federated model version, hospitals trained on, ensemble weights, threshold, probability, alert and timestamp.

Where the ten Phase-I agents went

Data Loader, Validation, Preprocessing, Temporal AnalysisAgent 1: Data Gathering and Preprocessing

AuditOrchestrator (logging, not a decision)
If asked "why only three agents?" An agent should own one complete responsibility and make its own decisions. Getting usable data, judging the sepsis risk, and explaining that risk safely to a clinician are three different responsibilities. The ten Phase-I steps were functions inside those three, so they are now grouped under the agent that owns them.

Every scheme is evaluated on each hospital's own test patients, and local models are also tested on the other hospital (cross-hospital), which shows how much a single-hospital model loses when used elsewhere.

Measures

  • Window level: AUROC, AUPRC, F1, accuracy, sensitivity, specificity, precision, NPV, alerts per 100 windows, Brier score, ECE.
  • Patient level: sepsis patients flagged before onset, lead time, and non-sepsis patients with a false alert.
  • Federation: validation AUROC, F1 and accuracy of the global model after every round, for every hospital; accepted and rejected updates per round; bytes exchanged per round.
